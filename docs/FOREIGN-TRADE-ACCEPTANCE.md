# 外贸办公场景深度验收

## 范围

模拟中国外贸企业员工通过 WorkBuddy 类办公客户端使用 WebCC。客户端采用官方 Anthropic Python SDK，连接线上 HTTPS 地址，解析真实 SSE、执行客户端工具并回传完整历史。测试在服务器执行，不使用个人电脑模型配置或登录状态。本次不是实际 WorkBuddy 软件验收。

每名员工使用独立的模拟工作区、独立测试密钥和同一线上资源池。文件读写与计算真实执行；模拟数据不包含真实客户信息。仅保存草稿，不向海外社交平台发布、不发送邮件、不支付或采购。

## 业务任务

| 岗位 | 任务 | 验收依据 |
|---|---|---|
| 外贸销售 | 读取产品和贸易条款、计算并生成英文报价 | 2500×3.20=8000，运费650，总价8650；交期与税费准确 |
| 社媒运营 | 局部修改 TikTok 三条英文脚本 | 移除无依据认证；LinkedIn 段与预算表保持原样 |
| 广告分析 | 计算 ROAS、CPL 并提出预算建议 | ROAS 6/3，CPL 20/50；不保证未来收益 |
| 海外客服 | 根据损坏投诉生成英文回复 | 5件刮伤、索取照片；不谎报退款或发货 |
| 采购 | 比较两家供应商 | A符合 MOQ 和20天要求，采购总价6750 |
| 库存专员 | 预留订单并修改库存 | 可用3500、预留2500；仓库与 SKU 保持 |
| 负责人 | 多文档汇总并提出行动计划 | 正确引用产品、广告与交期；区分事实和建议 |
| 销售助理 | 不存在文件、无权限、并发版本冲突 | 明确错误；重新读取并保留他人修改后保存回读 |

所有写入任务必须真实保存并再次读取。模型的最终答复与实际文档分别检查；自然语言质量由人工复核，自动关键词检查只用于发现候选问题。

## 并发与时间

并发档位：1、2、4、8名员工，每档执行全部8个岗位任务，共32个多步会话。保持线上全局并发上限4、每账号1；8名员工组检验排队与过载边界，不把8名在线员工等同于8个上游同时执行。

逐请求记录：

- 首个 SSE 事件时间：仅作连接观测，不作为有效内容速度。
- 首个有效内容时间：实际文本、工具参数或 Thinking 增量首次到达。
- 首段文本时间：用户可读文本首次到达。
- 请求总时间与结束原因；失败另计。
- 整个业务任务时间：包含多轮模型调用、工具执行与历史回传。

每档汇总 P50、P95、成功率、请求数与总时间。32个会话为业务验收样本，不代表长期生产 SLA。数据库占用采样检查峰值上游并发、账号分布及结束后释放；额外记录可用内存和负载。

## 重现

脚本：[foreign_trade_load.py](../experiments/foreign_trade_load.py)。仅在已配置的服务器 Python 环境执行；读取服务器私有环境文件，自动创建、撤销并删除临时测试密钥。原始记录和独立模拟文件位于 `/var/lib/webcc-cluster/trade-acceptance`。

## 实测结论

本轮未通过稳定办公使用的体验验收。49 个公网多步业务会话中，36 个完成调用、保存与回读；这不等于内容全部可直接对外使用。另执行3个隔离复现会话及普通聊天、联网、文件计算、取消和上下文边界检查。不是实际 WorkBuddy 软件验收，也没有官方 API Key 对照组。

### 并发速度

下表每档执行8个业务任务。请求耗时仅统计有完整结束事件的响应，失败另外记录。完成任务数表示自动工具/文件流程完成，不包含人工内容质量判定。

| 同时在线员工 | 完成任务 | 首个有效内容 P50 / P95 | 请求完整响应 P50 / P95 | 多步任务 P50 / P95 |
|---:|---:|---:|---:|---:|
| 1 | 5/8 | 6.15 / 10.13秒 | 6.78 / 12.68秒 | 32.62 / 66.91秒 |
| 2 | 6/8 | 5.12 / 8.81秒 | 6.41 / 11.20秒 | 31.11 / 46.07秒 |
| 4 | 6/8 | 5.63 / 11.00秒 | 6.77 / 12.51秒 | 35.82 / 47.39秒 |
| 8 | 7/8 | 9.85 / 16.67秒 | 11.05 / 16.88秒 | 54.01 / 73.01秒 |

基线单轮请求最大52.71秒；8用户组任务最大79.85秒，一次排队请求约15.31秒后返回429。若应用不展示工具进度，部分任务要30秒以上才有自然语言答复。

4用户组首段与完整响应分布尚可，但可靠性未达标。8用户组排队和时延明显增加。轮次固定1→2→4→8，模型随机性、账号状态和缓存均可能影响结果，不能从样本成功率反推“并发越高越稳定”。137个完成响应保存了逐轮精确时序；初测7个失败请求的首段时序未保留，其总时长估算单列。复测已补齐失败请求的精确时序，不能把估算当精确值。

8个失败相关岗位复测中5个完成、3个再次出现工具校验错误。三次失败请求分别为8.973、9.703、11.198秒，均为HTTP200后SSE报错。

采样峰值上游占用4，覆盖11个账号，未发现超过全局并发限制。最低可用内存约468.7MiB，最高1分钟负载0.38。该样本没有显示CPU成为主要瓶颈；没有足够依据为速度而更换编程语言。

### 已复现的具体原因

隔离复现捕获到模型返回 `{calls:[{name,input,text:""}]}`：业务工具名称及参数有效，但内部空text字段落在call对象内，根对象缺text，WebCC拒绝整轮。只在离线副本将空字段归位后，原工具参数仍通过全部Schema约束。这证明一种内部封装适配问题，不意味着其他校验错误都已定位；未部署修复。

### 清理与服务状态

89个运行文件摘要不变，健康检查200。生产临时密钥、占用、活动/待清理任务和本轮新孤立文件均为0；原有4个密钥保留。ccb1在测试期间触发连续3次通道失败隔离规则，保持隔离；这不等于已确认账号封禁，现有原因字段没有细分具体HTTP/传输错误。未修改ClewdR。

## 测试后的架构判断

按“先证据、后方案”处理。本轮建议继续复用Python、PostgreSQL、Redis与现有执行器，优先修复标准入口和解码可靠性，再用同一业务集复测；并发与扩容决策应以稳定任务成功率为前提。

| 实测问题 | 修正方向 | 需要保持的约束 |
|---|---|---|
| 默认入口没有工具调用 | OpenAI工具与Messages共用现有工具入口，转换请求/流式返回 | 只保留一套执行和历史校验，不复制规划器 |
| 有效参数被内部封装拒绝 | 对已确认的等价空字段结构归一化，再严格校验业务参数 | 不删除真实文本、未知字段或放宽工具参数约束；已执行动作不能重放 |
| 企业业务与受众混淆 | 让应用提供文档ID、目录发现、输出受众和资料依据 | 对客报价与内部成本分开；不编造认证或产品性能 |
| 长文档/上下文边界 | 范围读取、局部补丁、必要时压缩历史并保留工具状态 | 保留工具结果配对、当前版本及来源定位；错误明确可操作 |
| 沙箱缺包 | 明确环境能力、执行前检查依赖、选择受控预装模板或标准库 | 不在失败后无条件重跑可能有副作用的程序 |
| 排队和长任务等待 | 分阶段进度、清晰过载原因、取消和有界等待 | 不用心跳伪装内容速度，不盲目增加上游并发 |

参考用户提供的[公开分析仓库](https://github.com/liuup/claude-code-analysis)：[工具执行链](https://github.com/liuup/claude-code-analysis/blob/main/analysis/04b-tool-call-implementation.md)、[上下文管理](https://github.com/liuup/claude-code-analysis/blob/main/analysis/04f-context-management.md)、[持久恢复](https://github.com/liuup/claude-code-analysis/blob/main/analysis/04i-session-storage-resume.md)。采用的参考原则是工具输入校验与执行分层、按并发安全性调度、工具结果完整配对、压缩后恢复任务状态。分析仓库不是官方协议保证，也没有复制其源码进入项目。
