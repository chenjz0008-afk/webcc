# Claude API 兼容建设方案

核查日期：2026-10-06。状态：研究与设计，未部署本方案。

## 1. 目标与结论

目标是让外部用户使用平台密钥和平台 Base URL，通过 Anthropic SDK 调用 Claude 的主要数据接口。Claude Code 只是其中一个客户端。

兼容必须分别验证接口格式、功能语义、模型身份、资源生命周期和运行可靠性。HTTP 200、普通聊天成功或返回符合结构的 JSON，都不能单独证明完整兼容。

推荐保留现有管理平台和官方 ClewdR 镜像，增加原生 Anthropic 接入与能力路由。完整功能优先采用有相应权限的官方 API 上游；现有网页账号继续承接明确支持的请求。ClewdR 原生 Code 通道经 11 个账号隔离复核均出现 Free，当前账号未取得该通道资格；网页近似工具实验单独记录。

如果限定只使用现有网页 sessionKey，不接入其他上游，可以研究普通工具模拟和自建辅助服务，但没有证据支持与官方 API 全部能力等价。

来源：[API 总览](https://platform.claude.com/docs/en/api/overview)、[ClewdR](https://github.com/Xerxes-2/clewdr)。

## 2. 当前证据和问题

| 项目 | 已知情况 | 需要解决的问题 |
|---|---|---|
| 网页消息转换 | 部署版本重新构建 tools，仅按配置加入网页搜索；历史主要保留文本和图片 | 调用方自定义工具和 tool_result 不能完整进入网页请求 |
| 原生 Code 通道 | 11 个账号在服务就绪后复核均出现 Free / no_cookie_available | 当前免费资格不能兑现原生工具；先前 CLI 超时链路尚未完全定位 |
| 路由 | 开发分支已修复查询参数和模型列表鉴权，56 项模拟测试通过，未部署 | 动态资源路径、分页和更多 HTTP 方法仍待实现 |
| 请求转发 | 请求正文直接转发，头部采用有限列表 | 原生上游保留功能字段；按通道处理鉴权和功能头部 |
| 错误 | 当前多类上游错误转成通用消息 | 保留可恢复的协议错误信息，避免把参数错误判断为账号异常 |
| 流式 | 有首段有效内容检测和重试 | 覆盖工具、服务端工具、thinking、心跳和流内错误，避免合法非文本响应被视为空回复 |
| 模型 | 已发现免费网页账号可能忽略请求模型 | 不能仅修改响应 model 字段；严格请求应选能兑现该模型的上游 |
| 用量与结束原因 | 网页转换已出现空输出、结束原因和用量不准确 | 区分真实上游数据与本地估算，不伪造官方统计 |
| 密钥 | 当前使用一个平台 API 密钥 | 面向不同调用者建立独立密钥、撤销、限流和资源归属 |
| 自动更新 | 有基础生成验证和回滚 | 增加协议、工具、文件、批处理等候选版本验收 |

源码依据：[部署版本网页转换](https://github.com/Xerxes-2/clewdr/blob/061c6d8ac9187148f50c8d806b56962a7f222b6c/src/claude_web_state/transform.rs)。本地核查对象：`manager.py`、`updater.py`。

## 3. 可选技术路线

| 路线 | 实现方式 | 适用范围 | 关键限制 | 建议 |
|---|---|---|---|---|
| 官方 API 原生转发 | 平台鉴权后使用自己的官方凭据转发，保留原生请求和响应 | 最接近完整 Claude API 的行为 | 需要官方额度和相关模型、功能权限，仍须验证网关行为 | 完整兼容的主要路线 |
| ClewdR 原生 Code 通道 | 对有资格的账号使用已有 /code 路由 | 可能提供原生消息和客户端工具循环 | 订阅通道不等于完整官方 API；Files、Batches 等不能据此认定可用 | 先验证，按能力接入 |
| Sub2API 独立上游 | 部署为独立服务或参考其账号、OAuth、API Key 和会话调度机制 | 多凭据管理与调度 | 不能把网页 sessionKey 自动变成通用 API 权限；引入数据库和缓存等组件 | 可比较，不直接替换现有平台 |
| LiteLLM 原生透传 | 使用 Anthropic passthrough，再由现有入口统一路径和密钥 | 多上游、虚拟密钥、原生转发 | 功能仍取决于上游；其部署版本与具体端点要验证 | 上游类型增多时考虑 |
| Anthropic/OpenAI 协议转换 | 双向映射 tools、tool_use、tool_result、SSE | 已具有原生工具能力的其他后端 | 格式转换不会补出后端不存在的功能，也不能冒充 Claude 模型 | 备选协议路线 |
| 网页提示工具模拟 | 将工具定义写入提示词，解析约定结构，转换为 tool_use | 普通自定义函数调用原型 | 可能误解析、漏调用、参数错误；不能复制约束采样和签名 | 独立实验通道 |
| 自建搜索、抓取、沙箱、任务队列 | 自行执行服务，再映射为 API 内容块和资源 | 补充类似的业务功能 | 搜索质量、执行环境、计费、生命周期与官方不相同 | 明确标识自建实现 |
| 云平台 Claude | 接入平台提供的 Claude 模型，再适配到统一接口 | 有相应云平台资格时 | 不同平台的功能和端点并不完全相同 | 根据实际能力矩阵选择 |

项目依据：[Sub2API 主仓库](https://github.com/Wei-Shaw/sub2api)、[LiteLLM Anthropic 透传](https://docs.litellm.ai/docs/pass_through/anthropic_completion)、[Claude Reverse Proxy](https://github.com/janishar/claude-reverse-proxy)、[CC-Adapter](https://github.com/Jakevin/CC-Adapter)、[Claude Proxy](https://github.com/cloudomate/claude-proxy)。这些项目是技术参考，未在本服务器逐一验证。

提示工具模拟可参考 [0G Compute Adapter](https://github.com/claraverse-space/0G-Compute-Adapter) 的实现思路，但它不是本项目兼容性证明。

## 4. 能力与实现清单

| 编号 | 能力 | 在主项目中实现什么 | 上游条件或限制 |
|---|---|---|---|
| 1 | SDK 鉴权 | 支持 x-api-key 和 Bearer；转换成选定上游凭据；不同用户独立密钥 | 不向调用者暴露账号凭据 |
| 2 | Messages | POST /v1/messages；保留 system、messages、内容块与受支持参数 | 网页转换有内容损失，完整能力需原生后端 |
| 3 | 路由与查询参数 | 分开解析 path/query；保留 beta、分页；资源路由支持动态 ID | 不再只匹配完整字符串 |
| 4 | SSE | 原样转发事件顺序、心跳、JSON 增量、结束和流内错误；Nginx 不缓冲 | 不要求每个成功响应都含文字 |
| 5 | 自定义工具 | 保留名称、描述、input_schema；返回正确 tool_use ID/name/input | 原生后端优先，网页模拟需额外解析 |
| 6 | 工具结果 | 保留 tool_result、匹配 ID、is_error 和结果内容块 | 工具由调用方执行，网关不能擅自执行用户的终端或数据库工具 |
| 7 | 并行与多轮 | 保持多个调用和结果对应，不重写历史；覆盖空文本但有工具调用的合法响应 | 不同账号或模型切换须验证历史兼容性 |
| 8 | tool_choice | 按实际模型支持控制 auto、none、any、指定工具 | 不支持的组合明确报错，不静默忽略 |
| 9 | strict 工具 | 将 strict 与 Schema 原样送入支持的上游 | 本地校验加重试不能等同官方约束采样 |
| 10 | 结构化输出 | 保留 output_config 等实际支持的格式参数；验证截断与拒答情况 | 需要支持该模式的模型；不把普通 JSON 提示包装成相同保证 |
| 11 | thinking | 保留 thinking、签名、隐藏块、相关配置和原始历史 | 不生成或修改签名；网页思考摘要不能认定与 API 签名兼容 |
| 12 | 模型目录 | 实现列表、单模型查询和分页；只暴露路由可兑现的模型 | 不能用别名掩盖免费账号自动选模 |
| 13 | Token Counting | /v1/messages/count_tokens；对完整请求调用原生计数 | 本地字符估算不能称为官方计数 |
| 14 | Usage 与结束原因 | 保留 input/output/cache/server-tool 用量和 stop_reason | 网页数据缺失时不能编造精确值 |
| 15 | 图片、PDF、引用 | 保留 document/image/citations 块及受支持来源；验证引用定位 | OCR 或文本抽取会改变官方原生文档行为 |
| 16 | Files | 上传、列表、元数据、删除、适用的下载；实现资源 ID 归属和分页 | 文件绑定正确上游工作区；普通用户不能越权访问其他资源 |
| 17 | Batches | 创建、查询、取消、列表、结果下载；绑定任务到原上游 | 自建队列可以提供异步功能，但不等于官方批处理价格和语义 |
| 18 | Prompt Caching | 原样传递 cache_control、保持前缀、转发真实缓存用量 | 本地答案缓存不是官方提示缓存，不能伪报缓存命中 |
| 19 | 官方搜索与抓取 | 转发工具配置、服务端调用块、结果、引用和 pause_turn | 原生官方路线优先；网页搜索开关不是完整参数兼容 |
| 20 | 官方代码执行 | 转发工具、container ID、生成文件和后续请求 | 需要上游沙箱权限；自己的 Docker 沙箱属于另一种实现 |
| 21 | MCP 与工具发现 | 区分调用方 MCP 客户端与官方 MCP Connector；保留相关工具块 | 后者需要对应原生服务，单纯映射函数不能复制所有行为 |
| 22 | 程序化工具调用 | 保留 caller、容器和往返语义 | 依赖代码执行等上游能力，单一提示模板无法完整替代 |
| 23 | Skills 与其他扩展 | 按功能开关独立接入、管理版本与资源归属 | 需逐项审查端点和权限，不从普通消息成功推断支持 |
| 24 | 错误与限流 | Anthropic 错误结构、request ID、Retry-After；区分参数、权限、额度与故障 | 仅必要脱敏，不删除客户端需要识别的信息 |
| 25 | 重试与资源调度 | 按模型及功能筛选；保留现有并发限制；有状态任务绑定资源归属 | 输出开始后不重发；已执行服务端工具可能有重复副作用，不能只按“尚未输出”判定安全 |
| 26 | Beta 与版本更新 | 原生路线转发允许的功能头和扩展字段；维护测试版本清单 | 不支持的功能明确报错，不静默删字段 |

依据：[工具参考](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-reference)、[工具调用处理](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)、[严格工具调用](https://platform.claude.com/docs/en/agents-and-tools/tool-use/strict-tool-use)、[结构化输出](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)、[thinking 问题处理](https://platform.claude.com/docs/en/build-with-claude/thinking-troubleshooting)、[错误格式](https://platform.claude.com/docs/en/api/errors)。

## 5. 推荐架构与路由规则

```text
Anthropic SDK / HTTP 调用者 / 其他客户端
                   ↓
你的主项目：平台密钥、协议入口、限流、资源归属
                   ↓
能力路由：模型 + 功能 + 资源绑定 + 可用额度
          ├── 官方 Anthropic 原生上游
          ├── 已验证的订阅原生上游
          └── 现有 ClewdR 网页账号池
```

建议采用三种平台密钥策略。它们属于平台内部策略，不需要调用方额外修改请求格式：

| 策略 | 行为 |
|---|---|
| 严格原生 | 只选择能兑现请求模型及功能的原生上游；没有资源就明确失败 |
| 混合接入 | 仅将模型和功能均已验证的请求交给网页账号；其他请求走原生上游；设置费用上限 |
| 网页接入 | 只允许网页通道已验证的范围，不支持的功能返回明确错误 |

同一平台密钥可以使用多个上游，但平台密钥并不会让所有上游具有相同能力。文件、batch、container 等资源请求必须回到拥有该资源的上游。thinking、缓存和历史兼容性的约束需要分别验证，不能推断所有消息都必须绑定一个账号，也不能假定任意账号都可互换。

不应静默改用另一个模型、删除工具、删除 thinking 或转换文档。如果某项变化必须发生，应由平台策略明确允许并在文档说明。不能把网页账号的自动模型选择伪装成精确模型调用。

普通 Messages 透传应尽量保持无状态，不保存完整提示与回复。资源表只保存必要的用户归属、上游、ID、状态及时间；按不同调用者隔离。

## 6. 主项目的最小模块划分

| 模块 | 职责 |
|---|---|
| API 入口 | 认证、路径、参数、响应与 SSE；原生路线尽量不重写正文 |
| 上游适配 | official、subscription、web 三类；各自维护能力和认证 |
| 资源路由 | 文件、批处理和容器的归属；请求功能筛选和模型匹配 |
| 调度与故障 | 复用现有并发、冷却和隔离；增加通道相关错误策略 |
| 密钥管理 | 调用者、撤销、功能策略、额度上限与限流 |
| 兼容测试 | SDK、端点、内容块、失败场景及升级门槛 |

初期不必同时部署 Sub2API、LiteLLM 和多种适配器。优先复用现有主项目，单独增加官方原生适配；需求增长后再判断是否用成熟网关替代部分模块。保持 ClewdR 上游源码零修改。

## 7. 网页工具模拟的具体实现与边界

已完成基础真实实验：11 个账号首轮工具请求通过，3 个账号完成四轮读写。没有部署生产，不代表原生协议兼容。详见 [实验报告](WEB-TOOL-EXPERIMENT.md)。

这是一条独立实验路线：

1. 将工具名称、描述、Schema 和允许的选择规则序列化到稳定提示中。
2. 将过去的 tool_use、tool_result 和错误转换为清楚区分的历史文本，不让 ClewdR 过滤后丢失。
3. 要求模型使用明确的结构输出工具调用；仅解析约定区域，不把回答、代码示例或引用里的 JSON 当成真实调用。
4. 校验工具名称和参数，生成并保存一致的调用 ID；不允许模型调用未声明的工具。
5. 转换为 Anthropic tool_use 和 stop_reason，让调用方执行。
6. 下一轮还原工具结果，处理多个调用、失败和截断。重试必须有次数上限。
7. 流式时先完成工具判别与必要校验，再输出协议事件；这会增加首段延迟，无法保证与原生细粒度流式相同。

可以提高普通工具任务的可用性，但不能生成有效官方 thinking 签名、复制模型内部约束采样、取得官方服务端工具权限或精确复现隐藏用量。不要对外称为完全原生兼容。

## 8. 实施与验收顺序

| 阶段 | 交付物 | 验收 |
|---|---|---|
| 1：定义范围 | 模型与功能矩阵、严格密钥策略、端点清单 | 每项标明原生、近似或不支持，不能遗漏限制 |
| 2：原生基础 | 官方上游候选、Messages/Models/计数、错误与 SSE | Anthropic Python 和 TypeScript SDK 更换 Base URL/key 后完成真实调用 |
| 3：工具与 thinking | 自定义工具、多轮、并行、流式、严格格式和签名保持 | 单工具、多个工具、错误结果、截断、thinking 往返均真实通过 |
| 4：资源端点 | Files、Batches、资源归属与隔离 | 上传后引用、分页、删除、取消、结果读取和越权检查通过 |
| 5：服务端功能 | 搜索、抓取、代码执行、MCP 等已获权限功能 | 真实调用和结果块通过，不用模拟结果作为资格证明 |
| 6：账号池优化 | 经验证的网页/订阅能力接入，成本和并发策略 | 不改变严格请求语义，异常切换不重复工具副作用 |
| 7：更新维护 | 候选镜像与主项目兼容测试，逐个更新与回滚 | 新版本不兼容则保留已验证版本 |

模拟测试负责验证协议边界，真实测试验证上游能力；两者分别记录。覆盖非文本合法响应、500、429、错误参数、客户端断开、慢流、无心跳、响应中断和资源跨用户访问。

本机隐私要求继续执行：模型测试只在服务器隔离环境运行，不加载本机配置；检查请求内容；客户端无外网出口；账号出口固定代理并禁止失败直连。普通用户自己的 SDK 环境信息与本机联网行为由其客户端决定，平台不能保证其客户端完全不联网。

## 9. 完整性边界

普通模型数据 API 与组织 Admin、账单、Managed Agents 等是不同权限和产品范围。第一版明确覆盖主要模型数据 API，其他端点必须单独列入范围、接入和验证，不能用“完整兼容”笼统承诺。

功能、延迟、价格、额度、服务可用性和未来新增能力也应分别说明。通过代理调用官方上游最接近官方功能，但仍有网关延迟和自身故障，不意味着绝对无错误。

搜索证明了原生转发、协议转换、提示模拟和自建服务等路线存在；没有验证到一套可以把当前免费网页账号自动转换为完整官方 API 的现成方案。
